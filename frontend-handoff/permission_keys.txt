## PERMISSION SYSTEM MECHANICS (apps/core/permissions.py:40–55)

- Permission keys are stored per (user, workspace) in TeamMemberPermission rows.
- Absence of a row = DENIED (fail-closed).
- Workspace OWNERS (is_owner=True WorkspaceMembership) bypass key checks —
  IsWorkspaceOwner does NOT check TeamMemberPermission rows.
- SUPER_ADMINs use IsSuperAdmin, not workspace permissions.
- Views use HasPermissionKey permission class OR call has_permission() directly
  in the view body (e.g. SubjectListCreateView.post, ParentLinkView.post).

## OWNER-ONLY KEYS (keys that only matter for team members, not owners)

ALL keys above are for team members only. Owners have implicit full access.
Roles: TEACHER (owner), TEAM_MEMBER (needs explicit grants), STUDENT, PARENT
  — STUDENT and PARENT roles do not appear to receive TeamMemberPermission grants;
    the permission system is designed for TEAM_MEMBER granularity.

## DEFAULT SET FOR NEW TEAM MEMBER

UNKNOWN — no service code read that sets default permissions on invite acceptance.
The apps/accounts/services/team.py file was not read.
From the model: absence of row = denied. So a fresh TEAM_MEMBER has NO permissions
by default (fail-closed per REQ-ROLE-02).

## WRITE API

GET  /api/v1/team/{pk}/permissions/ → returns {"keys": [...]}
PUT  /api/v1/team/{pk}/permissions/ → body {"keys": ["KEY1","KEY2",...]}
     Replaces ALL permissions atomically (deletes old, inserts new).
     Invalid keys raise VALIDATION_ERROR.
     Requires IsWorkspaceOwner.
